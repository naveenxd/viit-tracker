# viit-tracker

Attendance tracking app for VIIT students — Kotlin Multiplatform + Compose
Multiplatform, Android-first.

[![Android release workflow](https://github.com/naveenxd/viit-tracker/actions/workflows/android-release.yml/badge.svg)](https://github.com/naveenxd/viit-tracker/actions/workflows/android-release.yml)

## What it does

- Attendance dashboard with per-subject standings and a safe-bunk buffer
- Day-by-day register: mark holidays and bunks, page through months
- Attendance projections with an interactive mark sheet
- Timetable with day-to-day swiping
- Home-screen attendance widget
- Faculty profile and academic record view
- Light, dark, and AMOLED themes; 24-hour clock and motion options
- In-app updates for sideloaded builds; Google Play updates for Play builds

## Tech stack

- Kotlin Multiplatform (Android app + shared UI/domain module)
- Compose Multiplatform / Jetpack Compose + Material 3
- Ktor client (OkHttp engine) + kotlinx.serialization
- AndroidX activity, lifecycle, security-crypto
- Gradle wrapper, AGP 9, Kotlin 2.x
- Python 3 for release tooling (`tool/release/`)

## Requirements

- JDK 21 (CI uses Temurin 21)
- Android SDK 36 (compileSdk / targetSdk 36, minSdk 24)
- Android Studio (latest stable recommended)
- Python 3 only if you run the release manifest tooling

Create `local.properties` if Android Studio has not already done it:

```properties
sdk.dir=/path/to/Android/Sdk
```

## Getting started

```bash
git clone https://github.com/naveenxd/viit-tracker.git
cd viit-tracker

# debug builds
./gradlew :androidApp:assembleGithubDebug
./gradlew :androidApp:assemblePlayDebug
```

Install a debug build:

```bash
adb install -r androidApp/build/outputs/apk/github/debug/androidApp-github-debug.apk
```

The debug package is `com.vignan.tracker.debug`, so it installs side-by-side
with a release build.

## Build variants

Two compile-time distribution flavors exist so the two update mechanisms can
never run in the same binary:

| | `github` | `play` |
|---|---|---|
| Application id (release) | `com.vignan.tracker` | `com.vignan.tracker` |
| Application id (debug) | `com.vignan.tracker.debug` | `com.vignan.tracker.debug` |
| Updates | in-app updater (`version.json` + APK download) | Google Play |
| `REQUEST_INSTALL_PACKAGES` | yes | **no** |
| `FileProvider` | yes | **no** |
| Release output | universal + per-ABI APKs | AAB |
| Settings label | `v1.1.0 · APK` | `v1.1.0 · Play Store` |

- Only one release build can be installed at a time (same package).
- GitHub and Play builds update through different channels.
- A device that installed the GitHub APK will never see Play updates, and vice
  versa.

## Update architecture

```text
github flavor:
  app open -> fetch version.json from raw.githubusercontent.com
           -> compare versionCode
           -> download matching APK
           -> verify SHA-256
           -> hand off to Android package installer

play flavor:
  app open -> Google Play In-App Updates API
           -> Play handles download / install
           -> immediate flow when Play update priority >= 4
           -> otherwise flexible download + "Restart" prompt
```

The GitHub manifest lives at `version.json` on `main`. It is regenerated by CI
after every tagged GitHub release. The Play flavor never reads it and has no
self-install permission.

## Building

### GitHub release APKs

```bash
VERSION_CODE=4 VERSION_NAME=1.1.0 ENABLE_ABI_SPLITS=true \
  ./gradlew :androidApp:assembleGithubRelease
```

Outputs:

```text
androidApp/build/outputs/apk/github/release/androidApp-github-universal-release.apk
androidApp/build/outputs/apk/github/release/androidApp-github-arm64-v8a-release.apk
androidApp/build/outputs/apk/github/release/androidApp-github-armeabi-v7a-release.apk
androidApp/build/outputs/apk/github/release/androidApp-github-x86_64-release.apk
```

Without `ENABLE_ABI_SPLITS=true` only the single APK is built.

### Play Store AAB

```bash
VERSION_CODE=4 VERSION_NAME=1.1.0 ./gradlew :androidApp:bundlePlayRelease
```

Output:

```text
androidApp/build/outputs/bundle/playRelease/androidApp-play-release.aab
```

Upload that AAB to Play Console. Play generates the device-specific split APKs;
do not upload a universal APK for the Play flavor.

> **Warning:** if `androidApp/key.properties` is absent, the release AAB is
> debug-signed. Never upload a debug-signed AAB to Play — Play locks the app
> signing key at first upload, and later release-key builds will be rejected as
> updates.

### Local AAB smoke test

```bash
bundletool build-apks \
  --bundle=androidApp/build/outputs/bundle/playRelease/androidApp-play-release.aab \
  --output=/tmp/viit-play.apks \
  --mode=universal
bundletool install-apks --apks=/tmp/viit-play.apks
```

This tests install/runtime only. Play In-App Updates only work for apps
installed from a Play track.

## Releasing

### GitHub / sideload release

1. Add `changelog/<version>.md` (one bullet per line).
2. Tag and push:

   ```bash
   git tag v1.1.0
   git push origin v1.1.0
   ```

3. CI publishes `viit-tracker-1.1.0.apk` plus per-ABI APKs to GitHub Releases.
4. CI regenerates `version.json` on `main`.
5. GitHub-flavor users see the in-app update sheet on next app open.

### Play Store release

1. Build or download the Play AAB (from CI artifact `aab-<run_number>`).
2. Upload it in Play Console.
3. Test on the Internal testing track first.
4. Promote through closed/open testing to production.
5. Play users update through Play; no `version.json` involved.

The AAB is **not** attached to GitHub Releases. GitHub Releases hold only
GitHub-flavor APKs.

### Version codes

- Play requires a strictly increasing `versionCode` that is never reused.
- CI uses `github.run_number` as the code for both jobs, so tagged releases get
  an increasing code automatically.
- If you build a Play AAB manually, use a code higher than every code already
  uploaded to Play.
- A workflow re-run keeps the same `github.run_number`. If that code was already
  uploaded to Play, bump it manually instead of re-running.
- Keep GitHub and Play codes aligned so users can switch channels if the signing
  certificates match.

## CI/CD

`.github/workflows/android-release.yml` runs on `v*` tags and on manual
`workflow_dispatch`:

- **build** — builds `assembleGithubRelease`, publishes APKs to GitHub Releases,
  then updates `version.json` on `main`.
- **play-bundle** — builds `bundlePlayRelease`, verifies the merged manifest has
  no `REQUEST_INSTALL_PACKAGES`, and uploads the AAB as a workflow artifact.

Manual runs upload APKs/AAB as artifacts instead of creating a release.

### CI signing secrets

```bash
gh secret set KEYSTORE_BAS64   < <(base64 -w0 /path/to/release.jks)
gh secret set KEYSTORE_PASSWORD --body '...'
gh secret set KEY_ALIAS        --body '...'
gh secret set KEY_PASSWORD     --body '...'
```

- Tag runs **fail** if the keystore secrets are missing, to avoid publishing a
  release that can never be updated.
- Manual runs without secrets produce debug-signed artifacts for sideload
  testing only.

## Signing and Play App Signing

Keep the same package (`com.vignan.tracker`) and the same app signing
certificate for both channels.

- Play App Signing signs delivered APKs with the app signing key.
- GitHub APKs must be signed with that same certificate to update Play installs.
- Best: enroll the existing release keystore as the app signing key on the
  first Play upload, if Play Console offers it.
- If Play uses a different app signing key, Android rejects cross-channel
  updates with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`; switching channels then
  requires an uninstall and loses app data.

The local keystore configuration lives in `androidApp/key.properties`, which is
gitignored. Never commit keystores or passwords. Keep an offline backup.

## Play Store maintainer notes

- The Play Console app package must be exactly `com.vignan.tracker`. A Play
  app's package name cannot be changed after creation.
- Play does not read `changelog/*.md`; enter release notes in Play Console.
- Keep the Data safety form and store listing current when app behavior changes.
- Test Play In-App Updates only through a Play testing track; sideloaded builds
  fail the update check gracefully.
- Maintainers should keep a local, untracked checklist with signing/upload
  details. Do not put credentials in this repository.

## Troubleshooting

**Play upload rejected: package mismatch**
The AAB must match the Play app package exactly. Confirm with
`aapt dump badging <aab-or-apk> | grep package`.

**Play upload rejected: version code already used**
Bump `VERSION_CODE`. Play never accepts a reused code.

**Play update never appears**
The app must be installed from Play (internal/closed/open track), not from an
APK. Also check the Play release has rolled out to the testers.

**GitHub in-app update never appears**
Check `version.json` on `main` has a higher `latest_build` than the installed
app, and that the release APK URLs resolve.

**`INSTALL_FAILED_UPDATE_INCOMPATIBLE`**
The new APK is signed with a different certificate than the installed app.
Either sign both channels with the same app signing certificate or uninstall
first.

**AAB will not install directly**
Expected — Android cannot install an AAB. Use Play, or `bundletool` for local
testing.
